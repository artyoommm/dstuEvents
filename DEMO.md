# DSTU Events — Лабораторная работа №4 (Реализация микросервисов)

## 📌 1. Архитектура системы и реализованные сервисы

В ходе работы была реализована микросервисная система для управления мероприятиями. Взаимодействие между клиентом и сервисами происходит исключительно через **API Gateway** (порт 8000).

### Таблица сервисов
| Сервис | Порт | Ответственность | База данных |
|---|---|---|---|
| **Gateway** | `8000` | Единая точка входа. Маршрутизация запросов, мок проверки JWT (проксирование заголовков). | — |
| **event-service** | `8001` | Управление жизненным циклом мероприятий, атомарное резервирование и освобождение мест. | SQLite (`event.db`) |
| **registration-service** | `8002` | Запись на мероприятия. Реализация **Саги**, проверка статуса студента, генерация QR-токенов. | SQLite (`registration.db`) |
| **attendance-service** | `8003` | Валидация QR-кодов волонтерами, фиксация посещений и неявок. | SQLite (`attendance.db`) |
| **profile-service** | `8004` | Хранение профилей студентов, начисление и списание баллов (рейтинга). | SQLite (`profile.db`) |
| **notification-service** | `8005` | Отправка email-уведомлений (через SMTP Mailpit) на основе событий. | SQLite (`notification.db`) |
| **RabbitMQ** | `5672` / `15672` | Брокер сообщений для асинхронного взаимодействия (Topic Exchange `dstu.events`). | In-memory |
| **Mailpit** | `1025` / `8025` | Перехватчик писем (SMTP-сервер для dev-окружения). | In-memory |

## 🛠️ 2. Использованные моки и заглушки

По условию лабораторной работы №4, полный подъем инфраструктуры из ЛР3 не требовался. Мы использовали реальный брокер (RabbitMQ) и почтовый сервер (Mailpit), но заменили тяжеловесные СУБД и авторизацию.

| Компонент из ЛР3 | Реализация в ЛР4 | Причина / Обоснование |
|---|---|---|
| **PostgreSQL** | **SQLite** | Допускается заданием. Легко запускается (файл на каждый сервис), не требует поднятия отдельных контейнеров СУБД. |
| **MongoDB** | **SQLite** | Замена документной БД на реляционную для `notification-service`. Схема гибкая, JSON-поля поддерживаются. |
| **Redis** (Кэш, TTL, Блокировки) | **SQLite** | Идемпотентность реализована через таблицу `idempotency_keys`. TTL резервов мест реализован фоновой задачей (asyncio) в `registration-service`. |
| **Keycloak** (Авторизация) | **Заголовки `X-Student-Id`, `X-Roles`** | Мок авторизации. Gateway просто пробрасывает эти заголовки. В реальной системе Gateway валидировал бы JWT от Keycloak. |
| **Kong** (API Gateway) | **FastAPI Proxy** | Написан минимальный прокси на Python, который маршрутизирует запросы по префиксам путей. |
| **RabbitMQ** | **RabbitMQ (Реальный)** | Поднят в Docker Compose. Сервисы используют `aio-pika` для pub/sub. |
| **Mailpit** | **Mailpit (Реальный)** | Поднят в Docker Compose. `notification-service` отправляет реальные SMTP-письма. |

## 🎬 4. Инструкция по демонстрации (через Postman)

Перед началом демонстрации убедитесь, что все контейнеры запущены (`docker compose up -d`).

1. Импортируйте коллекцию `DSTU Events Lab 4 (Full Demo)` в Postman.
2. В коллекции настроены переменные и скрипты автоматизации (ID событий и QR-токены передаются между запросами автоматически).

### Сценарий 1. Создание и публикация события
*   **Запрос `1. Create Event`:** Отправляет POST-запрос на создание мероприятия (с заголовком `X-Roles: admin`). Возвращает `201 Created` со статусом `DRAFT`.
*   **Запрос `2. Publish Event`:** Публикует событие. Возвращает `200 OK` со статусом `PUBLISHED`.
*   *Что происходит внутри:* `event-service` отправляет событие `event.published` в RabbitMQ. В интерфейсе RabbitMQ (очередь `notification-service.queue`) можно увидеть всплеск активности.

### Сценарий 2. Сага (Успешная регистрация и Отказ)
*   **Запрос `3. Register (Happy Path)`:** Заголовок `X-Student-Id: u-active`. 
    *   *Внутри:* `registration-service` синхронно проверяет профиль (ACTIVE) и резервирует место в `event-service`. Возвращает `201 Created` и выдает `qrToken`. Событие `registration.confirmed` летит в `notification-service`. В Mailpit приходит письмо.
*   **Запрос `4. Register (Banned Student)`:** Заголовок `X-Student-Id: u-banned`.
    *   *Внутри:* `registration-service` получает статус `BANNED` и возвращает `403 Forbidden`. Место в `event-service` не резервируется (Сага откатывается на первом шаге).

### Сценарий 3. Асинхронное взаимодействие (Посещаемость и Баллы)
*   **Запрос `5. Scan QR`:** Отправляет `qrToken` в `attendance-service`. Фиксируется статус `PRESENT`. Сервис отправляет событие `attendance.marked` в RabbitMQ.
*   **Запрос `6. Check Points`:** `profile-service` возвращает профиль студента. Видно, что `totalPoints: 10` (сервис прочитал событие из RabbitMQ и начислил баллы).
*   **Запрос `7. Mark No-Show`:** Отмечает неявку. Отправляется событие `attendance.no_show`.
*   **Запрос `8. Check Points`:** Баллы списываются. `totalPoints: -10` (10 - 20 за неявку).

### Сценарий 4. Проверка логов и уведомлений
*   **Запрос `9. Check Notifications`:** Запрос к внутреннему API `notification-service`. Показывает журнал отправленных писем (что сервис успешно прочитал события из RabbitMQ и сохранил их).
*   **Запрос `10. Cancel Event`:** Отмена мероприятия. `event-service` отправляет `event.cancelled`.
*   *Что происходит внутри:* Это событие ловят одновременно `notification-service` (шлет письма об отмене) и `registration-service` (массово отменяет регистрации в своей БД).

## 💡 5. Ключевые фишки для защиты лабы
1.  **Идемпотентность:** Если нажать "Send" в Postman дважды с одинаковым `Idempotency-Key`, второй запрос не создаст дубль в БД, а вернет сохраненный ответ первого.
2.  **Паттерн Сага:** В `registration-service` реализована компенсация. Если после резервирования места произойдет сбой, сервис вызовет `seats/release` и вернет место в `event-service`.
3.  **Отказоустойчивость RabbitMQ:** Если остановить `notification-service` и отправить запрос, сообщение останется в очереди RabbitMQ (статус Ready = 1). При запуске сервиса оно будет обработано (At-least-once delivery).
